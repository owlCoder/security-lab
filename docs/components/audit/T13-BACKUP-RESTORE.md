# T13: verified Audit backup and restore

Owner: Aleksandar Petrović, Team 12. Requirements: ADM-03, OPS-04; Audit integrity AUD-01/AUD-03.

## Scope

`AuditBackupRestoreTests` exercises PostgreSQL 17 `pg_dump -Fc` and `pg_restore` against
two newly created databases in the disposable container owned by the existing Audit runner.
It never reads a developer's `.env`, connects to the Compose database, or overwrites an
existing database. Database names are generated by the fixture. Its teardown drops only
those databases, and the runner removes the container and archives when it finishes.

The source contains real Identity and Audit schemas created by their EF migrations, synthetic
accounts/sessions and valid examples for every Audit catalog event. The real
`EfAccountStatusStore` blocks an account and revokes its session; the real
`PostgresTransactionalAuditWriter` writes the status event before the same transaction commits.
This is a storage/restore test of that production path, not a new HTTP authorization test.

The archive includes the entire test database, rather than separately timed dumps of the
Identity and Audit schemas. Other platform schemas and external files/keys are not seeded
here, so this test does not claim full-platform recovery coverage.

## Executable checks

The valid archive case verifies:

- all Audit event IDs, typed contents, details, schema versions and UTC timestamps;
- the blocked account, the same revoked session, and its linked status-change event;
- both EF migration histories;
- the restored ALWAYS trigger and owner UPDATE/DELETE rejection (`55000`);
- runtime SELECT/INSERT and rejection of UPDATE, DELETE, TRUNCATE, DROP and trigger disabling (`42501`);
- a fresh event can be persisted after restore and reapplying Audit migrations preserves data;
- the archive checksum remains unchanged through restore.

The negative case truncates a separate test archive. `pg_restore --exit-on-error
--single-transaction` must fail and the target must contain no Audit table. A process exit
status or a checksum alone is never treated as proof of a usable backup.

## Run and evidence

From the repository root, with PowerShell 7.4+, .NET 10 and Docker running:

```powershell
pwsh ./scripts/audit/test-postgres.ps1
```

The existing runner builds and tests the solution. It supplies the temporary container ID
and both test connection strings, and restores their prior environment values on exit.
Its TRX assertion now requires the restore fixture to have executed successfully, so CI
cannot silently pass by skipping these cases. Running `dotnet test` without that runner
explicitly skips this fixture. No additional workflow, package or production code is needed.
Evidence stays in the ignored `TestResults/audit-s09-*` directory.

succeeded and the final runner exited 0. TRX totals: 2,732 passed, 0 failed, 114 skipped

## Roles and operational ownership

`pg_dump` contains object ownership and grants, but not cluster-wide role definitions.
This test restores within the same disposable cluster: the runner provisions
`securitylab_audit_runtime` using the existing bootstrap script before tests run. The
test grants it SELECT/INSERT on the source Audit table; those grants must survive restore.
It does not claim to test recovery of roles onto a new cluster. A platform restore must
first provision the approved role definitions and credentials, preserve the intended
owners/ACLs, and run the permission checks again. Runtime roles must never become owners
or superusers to make a restore work.

The shared platform procedure belongs with the ADM owners. It must inventory each actual
database and external dependency, protect backup artifacts and keys outside Git, record
backup time/version/status, and verify recovery before marking a backup usable (ADM-11,
ADM-18). A whole-database snapshot preserves related business/Audit state in that database;
separate databases or external stores need an explicitly coordinated recovery strategy.
Retention, archive access, RPO/RTO, scheduling and any deletion policy remain D8 decisions
with ADM and the integration/security owners. This contribution does not introduce them.
